# 设备诊断（USB/HID 采集）

> 给**未适配设备**采证据的功能：先预检能力，再由用户确认采集，最后出离线报告与诊断包。
> 入口：主窗口「设备诊断」。代码：`src/VigilWatt.Core/Capture/`（纯逻辑）+ `Capture/Hid/`（Win32）。

## 1. 定位与边界

**做**：设备枚举、HID 接口 caps、经 HID API 实际读到的输入报告、用户勾选后的只读 Feature 报告、
用户在会话里**显式授权后手动发出的单帧**（唯一写入路径，见 §11）、离线报告与 ZIP 诊断包。

**不做**（不是没做，是不该在这个功能里做）：

| 项 | 原因 |
|---|---|
| 向设备写任何报文（含 Set Feature / Output Report） | `docs/hardware/safety.md` 事故一；采集句柄只申请 `GENERIC_READ`，从权限层面就写不了 |
| 枚举 / 扫描 report ID | 同上；只能从 caps 里**真实存在**的 ID 中选 |
| 原始 HID 报告描述符字节 | Windows 用户态没有该 API（见 §4） |
| USB 总线级抓包 | 需要 USBPcap 过滤驱动；本应用只检测、只指路，不内嵌 |
| 蓝牙 / 2.4G 空中通信 | 接收器只向上暴露 HID，无线链路不经过主机 USB 栈 |
| 解释报文含义 | 采集器只出证据，解释是适配器的事 |

**绝不自动切换采集方式**：任务与方式都是用户选的，代码里没有"采不到就换蓝牙/换接口"的分支。

## 2. 用户流程

页面是 4 段式，采集方式固定 USB/HID，用户要选的是**任务、设备、接口**：

1. **选任务与设备**
   - 「未知设备调查（找新协议）」：列出全部 HID **设备**，未适配的排前面，已适配的标 `已适配（插件名）`。
   - 「已支持设备诊断（排查读数）」：只列插件**正在认领**的设备；一个都没有时提示"可能插件都关着"，而不是装作没有设备。
   - 列表按物理设备聚合（**系统 ContainerId**，读不到才退回 `VID/PID`），**不是**把 30 个 HID collection 平铺出来——那正是用户第一次分不清的原因。
2. **选接口 + 预检（左右两栏）**：一台设备常有 7~10 个接口，每个接口标出 `有输入通道（in 19，report 0x07）` / `仅 Feature 通道（多为配置通道）` / `无输入 / Feature 通道` / `打不开（Win32 5）`；打不开的排最后（只能证明接口存在，采不到东西）。
   - 已适配设备直接推荐**插件实际认领的那个接口**（准确，不靠猜）。
   - 未适配设备按「厂商定义页 + 小报文」推荐并标「建议先试」；513 字节这类大缓冲通道会被排后（它通常不自发推送）。
   - **选中接口即自动预检**：`HidCapabilityProbe` 只读枚举时已有的 caps、不碰设备，没有理由再让用户点一次。
     右栏逐项给出 `可用 / 不可用 / 未验证 / 需要权限 / 需要额外工具`，非「可用」项必须带原因、影响、后续；
     列表**默认只列需要处理的项**（顶部一行 `预检 17 项 · 可用 11 · 不可用 2 · 未验证 1`，可用项折叠，
     勾「显示全部能力项」才展开）——全铺开时用户每次都得翻半天才找到该看的那两条。
     按钮「重新预检」留着给拔插后重读 caps。
   - 窗口宽 < 900px 时两栏上下堆叠（接口在上），与运行态两列同一阈值。
   - 该接口有输出通道（caps `out > 0`）时，可以勾选「允许向设备发送」——**这是唯一的写入路径**，见 §11。
3. **采集（按步骤引导）**：采集区给的是**一步一步的操作清单**，不是空白输入框——「操作设备 → 连接充电器 →
   断开充电器 → 关闭设备 → 重新开启设备」，每步写清怎么做（等 5 秒），点「完成这一步，下一步」自动打一条
   用户标记并前进；可「重做这一步」或「上一步」。每步实时显示「本步已采到 N 条报文」，做完能立刻看出哪一步没反应。
   **本步窗口 = 上一条标记到点「完成这一步」那一刻**（第一步从开始采集算起）——标记表示「这一步做完了」，
   不是「开始做」，所以窗口向前取而不是向后取。
   另留一个自定义标记框应付清单外的操作。

   **运行态换布局**（点「开始采集」后）：上面的选设备/选接口/预检三张卡收起，改成
   ① 顶部常驻**设备横幅**（产品名 / VID:PID / 接口段 / 已适配（插件名）或未适配，悬停看完整路径）——
   三张卡收起后这是唯一还能确认「采的是哪台、哪个接口」的地方，**不能省**；
   ② 常驻**步骤条**（5 段，当前段高亮、已完成打勾、每段带本步条数）——页面滚到哪都看得见第几步；
   ③ 左列当前步骤 + 采集控制，右列实时记录，两列并排（窗口宽 < 900px 自动退回单列）。
   停止后回到空闲态并自动滚到「结果与导出」，结果卡里也带设备名；**整场没有任何变化的分组会在结果卡上
   单独一行红字点出来**（不是只写在报告里——用户会看结果卡，不一定翻报告），InfoBar 也降为 Warning。
   否则很容易把「配置通道采到的恒定值」当成设备行为交出去。

   **记录卡顶部有「在等什么」一行**（用户反馈：进来一两秒没报文就以为没协议、直接退掉）。按已采秒数分档，
   给的是**动作**而不是固定数字——设备差异太大（雷柏醒着 3 秒一帧、睡着静默；迈从要先开会话才推）：
   `0–5 秒` 正在等第一帧 · `5–15 秒` 动一下设备 / 确认接口选对 · `≥15 秒` 这条通道可能不自发推送、换有输入通道的接口 ·
   收到数据后显示「已收到 N 条 · 首帧在 X.X 秒」。暂停时显示「已暂停：期间不读取设备」。

   **实时记录按步骤分段**：进入新的一步（或打自定义标记）时插一条分割行，后面那批报文属于哪一段一眼能对上；
   新报文进来列表**自动跟随到最新**（`ItemsStackPanel.ItemsUpdatingScrollMode="KeepLastItemInView"`），
   不用手动拖滚动条。之所以不做「最新排最上面」：倒序会让分割行只能落在它那一块的下方，反而分不清哪段是哪步。
   **不同协议通道用不同颜色**：左侧 3px 色条 + 类型文字同色，同一「记录类型 + report ID」始终同色
   （按首次出现顺序取 `UiPalette.SeriesColors`，每个会话重置）——多通道混采时扫一眼就能分开。

   **全键盘可操作**：`Ctrl+Enter` 完成这一步、`Ctrl+R` 重做、`Ctrl+←` 上一步、`Ctrl+P` 暂停、`Ctrl+S` 停止。
   采集鼠标/键盘本身时，**「关闭设备」那一步会把自己的光标弄没**，所以采集前会提示「用 Ctrl+Enter 完成这一步」。

   **电量核对（可选）**：从官方软件或设备屏幕上读到电量后填进去记一笔。它作为**外部参照**写进 `events.jsonl`
   （`kind=battery_reference`，带 `percent`），报告会列出「其后第一帧里值等于该电量的字节偏移」。
   偏移只是**候选**——某个字节恰好等于 78 很常见，要记几个不同电量（放电中 / 充电中）才能收敛。
4. **收尾有两条路**：
   - **停止并生成报告**（`Ctrl+S`）：自动写 `analysis.json`、`report.html`、`README.txt`、`vigilwatt-capture.zip`；
     可打开报告 / 打开文件夹 / 另存为 / 复制调查摘要。历史在 `data\captures\<会话>\`，重启后仍在。
   - **放弃这次采集**（`Ctrl+Shift+S`，警示色 + 二次确认，确认框默认落在「继续采集」）：停采集、关文件，
     然后把整个会话目录删掉——**不出报告，也不留原始记录**。删不掉（文件被占用）会如实写在结果里并给出目录路径，
     绝不假装成功。放弃后 `_active`/`_lastSession` 都清空，导出按钮全部禁用。

暂停 = 停止读取并释放句柄。**暂停期间没有记录 ≠ 没有数据**，报告里会写明这个缺口。

采到 0 条时页面会直接给下一步（换哪个接口、或提示该通道需要 Feature 读取），不会让用户以为"这设备没协议"。

## 3. 数据层级（不许混）

每条记录带 `layer` 字段：

| layer | 含义 |
|---|---|
| `device-enum` | 设备枚举与描述符信息 |
| `hid-caps` | caps 摘要（usage / 长度 / report ID） |
| `hid-api-input` | 经 `ReadFile` 实际读到的输入报告 |
| `hid-api-feature` | 经 `HidD_GetFeature` 实际读到的 Feature 报告 |
| `usb-bus` | USB 总线级（本应用不产生） |
| `wireless` | 蓝牙 / 2.4G 空中（本应用不产生） |

能读 HID 输入报告 ≠ 能读所有 USB 控制传输；接收器暴露的 HID ≠ 设备与接收器之间的 2.4G 链路。

## 4. 能力预检逐项（2026-10-24 本机实测结论）

| 能力 | 本机状态 | 依据 |
|---|---|---|
| 枚举设备 | 可用 | CfgMgr32 + `HidD_GetAttributes`，本机 30 个接口 |
| VID/PID/产品名/厂商名 | 可用 | `MCHOSE 2.4G Wireless` / `Compx`、`Rapoo Gaming Device` / `Rapoo` |
| 序列号 | 视设备 | Rapoo `2507-54L` 有；MCHOSE 无（返回 null，不是读失败） |
| 接口段与路径 | 可用 | 路径含 `MI_01&Col09` |
| 多接口归属 | 可用 | `DEVPKEY_Device_ContainerId`（SetupAPI）；实测雷柏 `24AE:1412` 的 MI_00/MI_01/MI_02 共用一个容器。读不到时退回 `VID/PID` |
| USB 总线号 / 地址 | 未验证 | 本版本未实现 |
| **原始报告描述符** | **不可用** | `hid.dll` 不导出；`IOCTL_HID_GET_REPORT_DESCRIPTOR` 六个候选码全 `ERROR_INVALID_FUNCTION`；注册表无该值 |
| caps 摘要 | 可用 | `HidP_GetCaps` + `GetValueCaps/GetButtonCaps`，`capsStatus=0x00110000` |
| 读输入报告 | 可用 / 需要权限 | 本机 30 个接口中 10 个 `CreateFile` 返回 5（保护 collection） |
| 读 Feature 报告 | 可用（须勾选 + 指定 ID） | `HidD_GetFeature`；ID 来自 caps |
| 写 Output / Set Feature | **不可用（本功能不写）** | `safety.md` 事故一 |
| 进程权限 | 可用（如实报） | 标准用户 / Medium 完整性，不提权 |
| 设备是否被占用 | **未验证** | HID 允许多句柄，无法可靠判定 |
| USB 总线抓包 | 需要额外工具 | 本机未安装 USBPcap |
| 蓝牙 / 2.4G | 不可用 | 层级限制 |

## 5. 文件格式

一会话一目录：`<数据目录>\captures\<yyyyMMdd-HHmmss>-<4位>\`

| 文件 | 内容 |
|---|---|
| `session.json` | 会话元数据、方式、环境、能力预检、计数 |
| `device.json` | 设备与接口元信息（含 caps 的 report ID 列表） |
| `records.jsonl` | 原始记录，每行一个 JSON |
| `events.jsonl` | 用户标记、暂停/继续、设备插拔 |
| `errors.jsonl` | 打开失败、读取失败、上限截断 |
| `analysis.json` | 分组统计、首末帧差异、**按步骤的字节变化**、标记前后对照 |
| `report.html` | 离线报告（内联 CSS，无脚本、无外链） |
| `README.txt` | 文件说明、格式、限制、隐私提示 |
| `backend.log` | 采集后端本会话日志 |

`events.jsonl` 里 `user_mark` 带 `stepId`（`device-action` / `plug-charger` / `unplug-charger` / `power-off` / `power-on`），
手写标记没有该字段——分析时可以按步骤分组，不受显示文案影响。用户输入的电量是 `kind=battery_reference` +
`percent`，**不是报文**，永远不会混进 `records.jsonl`。

`analysis.json` 的 `marks[]`：`recordsBefore` = 本步开始前的累计，`recordsInStep` = 本步窗口内的条数，
`newGroupsInStep` = 本步才出现的分组，`changes` = 本步窗口内首末帧的逐字节差异。窗口定义见 §2。
（2026-10-24 前的包用 `recordsAfter` / `newGroupsAfter`，那是**向后取窗口**的旧语义，同名的两列不可直接对比。）

`records.jsonl` 关键字段：`tsMono`（相对会话开始的毫秒，单调）、`tsUtc`、`layer`、`recordType`、`reportId`、`api`、`length`、`dataBase64`（**规范来源**）、`dataHex`（派生展示）、`status`。
`layer` 取值：`device-enum` / `hid-caps` / `hid-api-input` / `hid-api-feature` / `hid-api-output`（主机→设备，见 §11）/ `usb-bus` / `wireless`。
`status` 取值：`received`（收到）/ `sent`（主机发出）/ `failed`（失败，带 `error`）。

`device.json` 的 `groupKey` 是「一台物理设备」的分组键：正常是 `container:{guid}`（系统 ContainerId），
读不到该属性时退回 `vidpid:VID:PID`。`inputReportIds` 为空 = 该接口不使用 report ID（caps 里是 0），
此时报文首字节是**数据**不是 ID——`fields[].reportId` 同样写 null，别把 0 当 ID。

取不到的字段写 `null`，不填占位、不填 0。

## 6. 架构分层（R8 的落点）

```
Core/Capture/
  Model/纯逻辑   CaptureRecord/Event/Error、CapabilityItem、CaptureDeviceInfo、SessionInfo、枚举与字符串契约
  CaptureJson     JSONL 与 session/device/analysis 的读写契约
  CaptureAnalyzer 分组、重复率、首末帧差异、标记前后对照（只读输入）
  DeviceGroupKey  「一台物理设备」的分组键（ContainerId 优先，VID/PID 兜底）——纯函数，有单测
  HtmlReportGenerator / IssueSummaryBuilder / CapturePackageWriter
  CaptureStore   会话目录、历史列表、读回
  CaptureSession 状态机 + 汇聚 + 落盘 + 出包（source 通过 Func<ICaptureSource> 注入）
  ICaptureSource 采集来源抽象（未来 USB 总线 / BLE 都实现它）
  Hid/           唯一碰 Win32 的一层：枚举、ContainerId、预检、采集循环
```

只有 `Capture/Hid/` 碰 `hid.dll` / `setupapi.dll`；其余全部零 Win32/WinRT，因此能直接链进 `VigilWatt.Core.Tests`。
分组判断之所以能单测：键由纯函数 `DeviceGroupKey` 算，`Capture/Hid/` 只负责把 ContainerId 读出来交给它。

## 7. 测试与验证边界

单测（`dotnet test --filter "FullyQualifiedName~Capture"`，104 项）用可注入的假来源，**不依赖硬件**：
无适配器也能建会话、不自动切换方式、五档状态可区分、部分报告、字节/ID/时间落盘、读失败不伪造、
多接口不串、标记与记录分离、重复停止幂等、上限截断、差异不改原数据、HTML 段落与转义、ZIP 条目与路径穿越、历史重开。

**真机验证（2026-10-24，Rapoo VT3 `24AE:1412` `MI_01&Col09`）**：只读被动监听 6 秒收到 2 帧真实报文
`07 10 04 80 0C 80 0C 01 54 00 03 01 00 12 46 01 02 02 C6`（19 字节，report `0x07`），
`analysis.json` 分组/重复率/标记对照均正确，报告与 ZIP 生成成功。**全程零写入。**

**未在真机上验证**（只有模拟测试覆盖，不能当成真机已验证）。
2026-10-24 已真机覆盖：**步骤引导的 5 步推进 + 报告生成**（会话 `20261024-144642-62BB`，Rapoo `Col09`，30 条记录）；
其余各项仍待验：

| 项 | 怎么验 | 判据 |
|---|---|---|
| 步骤引导全流程 | 跑一轮 5 步：完成 / 重做 / 上一步 | 走完后标题变「全部步骤已完成」，最后一步显示真实条数（不是"记录中"） |
| 停止后再开一轮 | 停止 → 再开始 | 能开起来（旧版 `_active` 没清空会挡住） |
| 历史重看 | 历史列表点一条 | 能打开那条会话的 report.html |
| 另存为 / 剪贴板 | 点「另存为…」 | 弹系统保存框并落盘；弹不出时 InfoBar 提示已复制路径（两种都算过，**不能静默失败**） |
| 采集中拔设备 | 采集时拔 dongle | `events.jsonl` 有 `device_removed`、`errors.jsonl` 一条、会话转 Failed 但报告仍生成且记录保留 |
| 暂停 / 继续 | 采集时暂停 10 秒再继续 | 暂停期间记录数不涨，恢复后继续涨；报告里能看出这段缺口 |
| Feature 读取 | 选 Rapoo `Col06`（feat=33, id `0x08`）或 `Col07`（id `0x09`），勾选后选 ID | 出现 `recordType=hid_feature_report`、`api=HidD_GetFeature` 的记录；**返回全 0 也算链路通**（那是厂商配置通道） |
| 记录上限截断 | 20,000 条手动到不了 | **保持模拟测试覆盖，不为此加配置项** |

**不建议现在验**：与插件抢同一接口的相互影响——只有一次观察，验不出确定结论，别写进文档。

## 9. 这些证据够做什么、不够做什么

**够**：判断这台设备有没有厂商通道（在哪个接口）、报文长什么样与什么时候来、哪个字节像电量（配合「电量核对」）、
充电/开关机有没有对应的字节变化、以及当前权限能不能读到。

**不够**（要**从零写一个适配器**还缺这些）：

| 缺什么 | 为什么 | 怎么补 |
|---|---|---|
| **请求帧**（主机→设备） | 默认只读，包里只有设备→主机方向；适配器必须知道发什么帧（会话帧、查询帧） | 用 USBPcap 或 WebHID 从官方软件抓，见 `debugging.md` §1、§9；已知帧可用 §11 的手动发帧验证 |
| **报告描述符原始字节** | 用户态拿不到（§4）。已用 caps 明细（`device.json` 的 `fields`）部分弥补：每个字段的 usage / bit size / report count / logical range | 只能靠 USBPcap 或 Linux `usbhid-dump` |
| **多接口并行** | 一次只采一个接口；电量在 A 接口、按键在 B 接口时要人眼对齐 | 未实现，见 §10 |
| **总线级时序** | HID API 只给"报告到达"时间，看不出轮询间隔、控制传输、端点类型 | USBPcap |

> **caps 明细的真实价值有限，别高估**：厂商自定义的"数据管道"经常只声明 1 个按键位 + 一堆常量填充
> （2026-10-24 实测：雷柏 `MI_01&Col09` 的 19 字节报文，caps 里只有 **1 个 button cap**、value caps 为 0；
> 迈从 `MI_02` 倒是给了 `32 bit × 128`）。也就是说：**caps 能给结构时很好用，给不出时只能靠报文本身**。
> `fields` 仍值得存——它是"设备自己声明的结构"，比我们猜的可靠。

## 10. 后续可做（按性价比）

1. ~~**把 caps 明细落盘**~~ **已做**（2026-10-24）：`device.json` 的 `fields` 存每个字段的 usage / bit size /
   report count / logical range，报告里也列成表。注意上面那条：厂商管道经常给不出结构。
2. **多接口并行采集**：同一设备选多个接口同时采，解决"电量与按键分属不同接口"的关联问题。
3. 跨会话对比：两次采集的同一设备自动比对（现在只能人眼看两份报告）。

## 8. 已知限制与坑

- **「已支持设备诊断」是插件耦合的**：插件在轮询同一接口时，你看到的报文里有一部分是**插件自己查询的应答**
  （2026-10-24 迈从 0x13 通道：`13 4A` 三帧间隔正好 60 秒，与主轮询一致）。这既是"能看到插件收到什么"的好处，
  也是干扰——不能把这些当成设备自发行为。插件关掉后该通道大概率完全静默。
- **0 条记录不等于没有协议**：MCHOSE `41E4:2001 MI_01&Col01`（`0x13` 会话通道）被动监听 6 秒零报文——
  它要先开会话才推送，而本功能默认不写设备（除非用户在 §11 里手动发帧）。报告里固定写这句话。
- **选错接口是最常见的"采不到"**：2026-10-24 用户第一次采集选了 Rapoo 的 `MI_02`（513 字节大缓冲通道），
  6 秒 0 条。同一个 dongle 的 `Col09`（19 字节）能正常出报文。所以设备必须先按物理设备聚合、接口必须标出有没有输入通道。
- **嵌套滚动**：页面是 `ScrollViewer` 套 `ListView`，内层必须设 `ScrollViewer.VerticalScrollMode="Disabled"`，
  否则滚轮被内层吃掉、整页滚不动。只有记录列表保留内层滚动（它是日志，本来就该单独滚）。
- `HidDeviceScanner.Scan()` **不能复用**：打不开就 `return null` 且吞异常、还带缓存，采集侧要看到失败原因。
- 采集句柄只申请 `GENERIC_READ`；`HidDeviceInfo.OpenRead()` 的 `FileStream` 也用 `FileAccess.Read`，
  否则 `CanWrite` 会骗人。
- 同一接口被本应用插件同时持有时，采集仍能收到报文（2026-10-24 观察一次），但**不能据此承诺互不影响**。
- **记录上限默认 2 万条 / 8 MB**；触顶后停止记录并在报告里写「已截断」。
- **没收尾的会话**：应用在采集途中被关掉时，会话目录与原始记录还在，但没有 `report.html`/zip。
  历史里这类条目会标「未生成报告（会话没收尾）」，点开是打开目录而不是报告——别让它看起来像数据丢了。
- **「没报告」有两种，别混**：① 用户主动放弃 → 目录已被删除，历史里查不到（这是设计，不是丢失）；
  ② 应用中途退出 → 目录还在、`session.json` 的 `state` 停在 `running`/`paused`。所以 `state + 是否有 report.html`
  就能区分，不需要为「放弃」新增枚举值。
- **分组依赖系统给的 ContainerId，两种退化要知道**：设备不提供 container 描述符、Windows 又没把接口归一 →
  同一个 dongle 可能仍被拆成多行（退回修之前的样子）；属性读不到 → 退回 `vidpid:` 键，同型号两只并成一台。
  排查时先看 `device.json` 的 `groupKey` 是 `container:` 还是 `vidpid:`。
- **整场没变 ≠ 采到了状态**：配置/握手通道会一直返回同一帧——雷柏 `Col06` 的 feature `0x08` 实测 43 帧全是
  `02 00 … 00`，充放电、开关机全程一个字节都没动。判定门槛是**同一分组 ≥5 帧且只有 1 种内容**，报告和摘要
  会直接写「没有任何变化，可能不是状态通道」，别让用户自己从「不同内容 1 / 重复率 98%」去推。

## 11. 手动发帧（唯一的写入路径）

默认**不写设备**：句柄只申请 `GENERIC_READ`。只有用户在开始采集前勾选「允许向设备发送（手动发帧）」，
该会话才以读写方式打开句柄（`OpenReadWrite`），运行态出现「手动发帧」卡片。
**采集器从不自己发帧**——每一次发送都是用户点出来的，每次都有二次确认。

### 为什么需要它

会话型通道（如迈从 `0x13`）要主机先发查询/会话帧，设备才回。纯被动监听只能看到"有人在问"时的应答，
看不到"问的是什么"，也就写不出适配器。手动发帧让"已知一帧 → 验证响应"这件事可做。

### 帧从哪来（用户问过，写全）

1. **USBPcap + Wireshark**（最通用）：装 USBPcap，用 Wireshark 抓 USB，操作一次官方软件（切电量/灯光/DPI），
   找 `URB_CONTROL out` / `URB_BULK out` 的 payload，抄下来。
2. **厂商文档 / 开源逆向项目**：有现成请求帧的直接用。
3. **本工具的旁路**：插件轮询时能看到它问出来的应答（`api=ReadFile`），但**看不到请求帧**——那必须靠 USBPcap。

**不要靠猜**：按 report ID 逐字节试正是 `safety.md` 事故一的成因。

### 硬约束

- 长度必须等于该接口 caps 的 `outputReportLength`（HID 对长度严格，先挡掉再发）
- 若接口用 report ID，首字节必须是 caps 里存在的 ID
- 发出的帧进 `records.jsonl`：`layer=hid-api-output`、`api=WriteFile`、`status=sent`；失败则 `failed` + 原因
- 记录列表用 `→` 前缀 + 「发出」标方向；报告「采集方式」段会写「本会话由用户手动发出 N 帧」
- 未勾选授权的会话**从权限层面就写不了**（句柄没有 `GENERIC_WRITE`）
