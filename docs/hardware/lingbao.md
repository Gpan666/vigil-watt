# 凌豹 LINGBAO M5PRO Max（接收器 3151:402D）

> 2026-10-24 新增；2026-10-25 用官方驱动运行时抓包**修正了命令字节**（`0x83` → `0xF7`）。
> 早期版本发 `0x83` 时接收器只回缓存/全 0，插拔接收器后必现离线，根因就在这里。

## 1. 设备与接口

| 形态 | VID:PID | 配置接口 | 状态 |
|---|---|---|---|
| 2.4G 接收器 | `3151:402D` | `MI_02`，usagePage `0xFFFF` / usage 2，feature 65 字节 | 本机实测打通 |
| 有线/直连 | `3151:4026` | 同上，但只会把命令原样回显、不返回状态 | **不认领**（2026-10-25 实测） |

- 厂商集合**只有一个 feature report（report ID 0）**，没有 output/input 通道。
- `3151` 是荣源/ROYUAN 共用号段：同 VID 的键盘/鼠标型号有几百个，判据必须带 PID + usage + feature 长度。

## 1.2 帧格式（2026-10-25 抓包修正）

官方驱动实际发送的是 **`F7` 状态查询**，不是官方 JS 里的 `FEA_CMD_GET_BATTERY = 0x83`：

```
hid_send_feature_report(dev, 00 f7 00 00 … 00, 67)     # report ID 0 + f7 + 全 0，无校验和
```

- 官方驱动传 **67 字节**（1 + 66），本机实测 **65 字节**（1 + 64）同样有效，插件用 65。
- **没有校验和**：早期按 ROYUAN 公开文档的 `0xFF - sum` 实现是错的——那个规则适用于另一套键盘协议。

## 1.3 响应

`HidD_GetFeature(0)` 返回 65 字节（含 report ID）：

```
[0]=00  [1]=接收器 ack（0/1）  [2]=设备返回码  [3]=电量%  [4]=固定 0x01  [5]=充电位（1=充电中，0=放电）
```

本机实测（2026-10-25）：

```
放电 95%   00 00 00 5f 01 00 01 02 …
充电 90%   00 00 00 5a 01 01 01 02 …     # 插上充电线，鼠标切到有线模式，接收器仍报状态
```

- `[1]` 两个值都见过（0 = 缓存应答 / 1 = 已受理），不作判据；`[2]` 必须为 0。
- `[5]` 是**充电位**：插线 `01`、拔线 `00`，同一晚两种状态各采一次确认。
- **接收器刚插上、没开过官方驱动时，第一条 `f7` 就能返回电量**——不需要任何初始化握手。

## 1.4 未闭合点

1. 有线接口 `3151:4026` 只会把 `f7` 命令**原样回显**、不返回状态，因此插件**不认领它**；鼠标插线时靠接收器（`402D`）继续读数，实测正常。
2. "已充满"没有单独状态位，收尾交给 `ChargingStateMap`（未充电且 100% ⇒ Full）。

## 1.5 写入与开关

查询是只读命令，但仍要写 feature report，所以插件**默认关闭**，插件开关即写入授权
（`AppSettings.PluginEnabled["Lingbao"]`，见 [safety.md](safety.md) §3.1）。

## 1.6 证据来源

- **运行时抓包**（2026-10-25）：Frida 注入官方驱动的 `iot_driver_v190.exe`，hook `hid_send_feature_report` /
  `hid_get_feature_report`，直接读到它每 10 秒发一次的 `00 f7 00 …` 与回帧。脚本见工作区 `tools/capture_hid.js`。
- **官方驱动 JS**：设备表条目 `vid:12625,pid:16429,name:"mouse_pan1080_xmg_m5promax_1k_8k",displayName:"M5PRO Max",featureReportByteLength:65`。
- 早期按 JS 的 `getBattery()`（`0x83` + BIT7）实现，实测只拿到缓存/全 0——**JS 里的命令不是这条链路的实际帧**，以抓包为准。
